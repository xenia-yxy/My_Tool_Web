# 阶段 2：用户端登录与后台管理 Ne/Ti/Ni/Te 过程文档

记录日期：2026-05-25

## 文档定位

这份文档用于保存第二阶段从自由探索到可开发落地的关键判断。

它不是逐字聊天记录，而是阶段 2 PRD、UI 设计、开发计划和验收清单的上游依据。

本阶段对上一版“单管理员内容发布闭环”的理解做一次修正：

```text
公开站点上的“登录”不是后台管理员登录。
它是提供给用户使用的前台登录入口。
后台管理需要单独做成一个管理系统，用来管理用户端的个人 Web。
```

因此阶段 2 的核心不再是把 `/login` 当作管理员登录，而是先把前台和后台的身份边界拆清楚。

## 0. 第二阶段触发背景

阶段 1 解决的是公开门面：

- 访客第一眼知道这是一个个人 AI 实践者的数字据点。
- 首页能承接知识库、工具、项目、SOP 服务和联系入口。
- 首页视觉从通用模板感收束为 `AI Practice` 个人品牌。
- 悬浮小助手成为后续理解网站与知识库的创新入口。

阶段 1 末尾已经在公开首页头部保留了“登录”入口。这个入口的产品含义需要重新定义：

- 它不应该直接进入后台管理。
- 它应该是用户端的公开登录入口。
- 后台管理应该是另一个独立区域，不混在公开站点的用户体验里。

这意味着第二阶段的重点是：

```text
前台用户登录 + 独立后台管理系统 + 后台管理前台个人 Web 内容。
```

## 1. Ne-A 自由探索

围绕第二阶段，先打开问题：

```text
如果公开站点上的登录是给用户用的，而后台管理要单独做，第二阶段最小但有效的一步是什么？
```

自然冒出的方向：

- 前台需要一个公开登录页，让用户知道这里未来不是只有浏览，也可以进入自己的用户状态。
- 前台登录不能暴露后台管理感，不能让普通用户以为自己进入管理系统。
- 后台需要独立入口、独立登录、独立布局。
- 后台用于管理用户端个人 Web，包括首页内容、知识库文章、工具入口、项目展示、SOP 服务和联系信息。
- 后台管理不应该出现在公开导航里。
- 公开站点的“登录”可以跳转到 `/login`。
- 后台管理入口可以使用 `/admin/login` 或直接保护 `/admin`。
- 前台用户和后台管理员必须有角色区分。
- 未来用户登录后可能进入个人中心、收藏、工具使用、会员内容或专属助手。
- 但第二阶段不能直接做完整会员系统。
- 后台可以先管理最关键的内容对象：文章 / 笔记 / 公开知识库。
- 后续再扩展到首页区块、工具、项目、服务配置。

也有一些容易膨胀的想法：

- 用户注册。
- 用户个人中心完整功能。
- 用户收藏、点赞、评论。
- 会员体系。
- 知识付费。
- 多租户个人站。
- 后台可视化搭建首页。
- AI 小助手接入用户数据。
- 复杂 RBAC 权限系统。

这些方向可能是未来能力，但不应该全部塞进阶段 2。

## 2. Ne-B 结构化整理

### 2.1 角色分层

第二阶段至少要区分三类角色。

公开访客：

- 不登录也可以访问首页、知识库公开内容、工具展示、项目展示、服务入口。
- 可以通过公开首页的“登录”进入用户端登录页。

前台用户：

- 通过公开登录入口登录。
- 登录后进入用户端区域，而不是后台管理。
- 阶段 2 可以先只提供最小用户态，例如登录成功页、账户入口或用户中心占位。
- 后续可以扩展收藏、工具使用、会员内容、专属助手等能力。

后台管理员：

- 通过独立后台入口进入。
- 管理用户端个人 Web 的内容和配置。
- 不通过公开首页普通“登录”进入后台。
- 拥有内容发布、撤回、编辑、删除等管理权限。

### 2.2 前台与后台边界

前台用户端：

```text
/
/login
/account 或 /me
/knowledge
/knowledge/[slug]
/tools
/projects
/services
```

后台管理端：

```text
/admin/login
/admin
/admin/notes
/admin/notes/new
/admin/notes/[id]
```

边界原则：

- 公开首页导航里的“登录”指向用户端登录，不指向后台。
- 后台管理入口不作为公开访客的主路径。
- 前台用户登录后不能访问后台。
- 后台管理员登录后才能访问 `/admin/*`。
- 后台管理页面使用后台布局，不沿用公开首页首屏风格。

### 2.3 核心场景

场景 1：普通用户登录。

```text
公开首页 -> 点击登录 -> 用户登录页 -> 登录成功 -> 用户端账户页
```

阶段 2 可以先让用户登录后进入一个最小账户页，说明后续将开放工具、收藏、会员或专属能力。

场景 2：管理员进入后台。

```text
后台入口 -> 管理员登录 -> 后台首页 -> 管理用户端个人 Web
```

场景 3：管理员管理公开内容。

```text
进入后台 -> 新建/编辑文章 -> 发布 -> 前台知识库展示
```

场景 4：管理员调整公开内容状态。

```text
进入后台 -> 撤回或删除内容 -> 前台不再展示该内容
```

场景 5：访客阅读公开内容。

```text
首页/导航 -> 知识库 -> 文章详情 -> 返回首页或联系
```

## 3. Ti 提纯

### 3.1 真实需求

第二阶段真正要解决的是身份边界和管理入口，而不只是做一个登录表单。

必须满足：

- 公开登录是用户端登录。
- 后台登录是管理员登录。
- 两种登录不能混用。
- 前台用户不能进入后台。
- 后台管理员可以管理用户端个人 Web 内容。
- 后台写操作必须服务端校验管理员权限。
- 公开知识库只能展示后台发布的内容。
- 后台管理必须独立布局。

### 3.2 暂缓需求

暂缓：

- 用户注册。
- 找回密码。
- OAuth 登录。
- 用户收藏、评论、点赞。
- 会员体系。
- 知识付费。
- 多租户个人 Web。
- 完整 RBAC。
- 可视化页面搭建器。
- AI 小助手真实知识库检索。
- 后台管理所有首页区块。

这些能力进入后续候选池，不进入阶段 2 P0。

### 3.3 技术约束

已有技术底座：

- Next.js App Router。
- Prisma + PostgreSQL。
- Auth.js / NextAuth.js 依赖已存在。
- `User`、`Note`、`Account`、`Session`、`VerificationToken` 模型已存在。
- 当前 `Role` 只有 `ADMIN`，需要支持前台用户与管理员区分。
- 当前 `NoteStatus` 为 `PRIVATE` / `PUBLISHED`。

关键判断：

- 需要扩展角色概念，至少区分 `USER` 和 `ADMIN`。
- 前台用户登录和后台管理员登录可以复用认证底座，但登录入口、重定向和权限校验必须分开。
- 阶段 2 不开放用户注册，可以先由后台或种子数据创建用户；如果要开放注册，需要单独确认。
- 后台管理内容仍先围绕 `Note` 做，因为它是个人 Web 内容沉淀的最小对象。
- 用户端登录后的功能先做最小账户页，不做完整用户系统。

### 3.4 关键风险

风险 1：前台登录和后台登录混在一起。

控制方式：

- `/login` 只给前台用户。
- `/admin/login` 只给后台管理员。
- 公开导航只出现用户端登录。
- 后台入口不作为普通访客路径展示。

风险 2：阶段 2 范围膨胀成完整会员系统。

控制方式：

- 用户登录后先进入最小账户页。
- 不做注册、收藏、评论、付费。

风险 3：后台管理范围过大。

控制方式：

- 后台 P0 先管理知识库内容。
- 首页模块、工具、项目、服务配置放到后续阶段。

风险 4：权限只靠前端判断。

控制方式：

- 后台页面服务端校验管理员角色。
- 后台写操作服务端校验管理员角色。
- 前台用户即使知道 `/admin` 路径也不能访问。

## 4. Ni 收束

第二阶段主轴：

```text
建立前台用户登录与独立后台管理的身份边界。
让公开站点可以提供用户登录入口，同时让管理员通过独立后台管理用户端个人 Web 内容。
```

核心闭环：

```text
用户端：
公开首页 -> 用户登录 -> 用户账户页

后台端：
管理员登录 -> 后台管理 -> 发布内容 -> 前台知识库展示
```

阶段成功的标志不是用户系统多完整，而是：

```text
公开登录不会进入后台，后台管理也不会暴露给普通用户。
管理员能通过独立后台管理前台个人 Web 的第一类内容：知识库文章。
```

## 5. Te 落地摘要

### 5.1 阶段名称

```text
阶段 2：用户端登录与后台管理分离 MVP
```

### 5.2 P0 必做

前台用户登录：

- `/login` 用户端登录页。
- 登录入口来自公开首页头部“登录”。
- 登录成功后进入 `/account` 或 `/me`。
- 登录失败有明确提示。
- 用户端登录不进入后台。

用户账户最小页：

- `/account` 或 `/me`。
- 显示当前登录用户基础信息。
- 说明后续将开放工具、收藏、会员或专属能力。
- 提供返回首页和退出登录。

后台管理入口：

- `/admin/login` 管理员登录页。
- `/admin` 后台首页。
- 未登录或非管理员访问 `/admin/*` 时跳转 `/admin/login` 或显示无权限。
- 后台使用独立管理布局，不使用公开首页导航。

后台内容管理：

- `/admin/notes` 内容列表。
- `/admin/notes/new` 新建内容。
- `/admin/notes/[id]` 编辑内容。
- 支持保存标题、slug、摘要、正文。
- 支持发布、撤回、删除。
- 删除必须二次确认。

前台知识库：

- `/knowledge` 展示后台发布的文章列表。
- `/knowledge/[slug]` 展示已发布文章详情。
- 未发布内容不能被前台访问。

权限与安全：

- 至少区分 `USER` 和 `ADMIN`。
- 前台用户不能访问后台。
- 后台写操作必须服务端校验管理员身份。
- 密码不能明文存储。

### 5.3 P1 可做

- 后台创建前台用户。
- 后台用户列表。
- 用户登录后显示可访问工具入口。
- 保存成功/失败提示。
- slug 自动建议。
- 内容状态筛选。
- 管理员退出登录。

### 5.4 P2 后置

- 用户注册。
- OAuth。
- 找回密码。
- 收藏、评论、点赞。
- 会员体系。
- 付费。
- 多租户个人 Web。
- 完整 RBAC。
- 首页可视化配置。
- AI Practice Assistant 接入用户状态或知识库检索。

### 5.5 数据对象

建议调整：

```text
Role:
  ADMIN -> 后台管理员
  USER  -> 前台用户
```

继续沿用：

```text
User
Note
```

`Note.status` 使用：

```text
PRIVATE   -> 后台私密内容 / 未发布草稿
PUBLISHED -> 前台公开文章
```

后续可能新增：

```text
SiteConfig
Tool
Project
Service
```

但阶段 2 P0 不新增这些复杂对象。

### 5.6 页面清单

| 路由 | 角色 | 说明 |
| --- | --- | --- |
| `/login` | 前台用户 | 用户端登录页 |
| `/account` 或 `/me` | 前台用户 | 用户账户最小页 |
| `/admin/login` | 管理员 | 后台管理登录页 |
| `/admin` | 管理员 | 后台首页 |
| `/admin/notes` | 管理员 | 内容管理列表 |
| `/admin/notes/new` | 管理员 | 新建内容 |
| `/admin/notes/[id]` | 管理员 | 编辑内容 |
| `/knowledge` | 访客 / 用户 | 已发布文章列表 |
| `/knowledge/[slug]` | 访客 / 用户 | 已发布文章详情 |

### 5.7 验收标准

- 公开首页“登录”进入 `/login`。
- 前台用户登录成功后进入 `/account` 或 `/me`。
- 前台用户不能访问 `/admin`。
- 管理员通过 `/admin/login` 登录。
- 管理员登录后可以进入 `/admin`。
- 未登录访问 `/admin/*` 会被拦截。
- 非管理员访问 `/admin/*` 会被拒绝。
- 管理员可以新建、编辑、发布、撤回、删除知识库内容。
- 发布后文章出现在 `/knowledge`。
- 文章详情页只展示已发布内容。
- 删除内容前有二次确认。
- 前台和后台 UI 风格有明显区分。
- `pnpm lint` 通过。
- `pnpm build` 通过。

### 5.8 不做范围

第二阶段不做：

- 用户注册。
- OAuth。
- 找回密码。
- 会员。
- 付费。
- 评论、点赞、收藏。
- 多租户。
- 完整 RBAC。
- 后台可视化搭建首页。
- 图片上传。
- 工具运行后台。
- AI 小助手真实知识库检索。

## 6. 后续能力候选池

第二阶段完成后，可以根据实际使用继续扩展：

- 用户注册。
- 用户中心能力。
- 用户收藏和工具使用记录。
- 后台用户管理。
- 首页模块配置。
- 工具、项目、SOP 服务后台管理。
- AI Practice Assistant 接入公开知识库。
- 会员和付费能力。

这些能力需要在前台用户登录与后台管理边界跑通后再做。

## 7. 是否进入下一阶段

建议进入下一步：

```text
为阶段 2 编写开发文档和实现计划。
```

进入条件：

- 确认公开站点“登录”是前台用户登录。
- 确认后台管理是独立系统，不复用公开登录入口。
- 确认阶段 2 P0 只做用户端登录、后台管理入口、后台内容管理和前台知识库展示。
