# AI 驱动从想法到产品交付协作规范

整理日期：2026-05-21

定位：从原始 idea 到自由探索、PRD、MVP、企业级产品化、UI 设计、技术方案、开发上线和复盘迭代的 AI 协作规范

适用范围：Web、移动端、H5、小程序、企业后台、SaaS、AI 工具、业务系统、内容产品、低代码/生成式开发流程

---

## 0. 文档目标

这份文档解决一个核心问题：

```text
如何把一个原始 idea，通过 AI 协作，稳定地变成可验证、可设计、可开发、可验收的项目？
```

它不是一套写死的流水线，也不是一组孤立提示词。

它是一套带有人工确认闸门的协作流程：

```text
AI 负责发散、整理、提炼、生成、评审。
人负责判断、确认、取舍、修正、推进。
```

最终目标是得到一套可以指导产品判断、设计、开发、上线交付和后续迭代的文档体系：

```text
产品需求文档
MVP 范围文档
后续能力候选池
MVP UI 与交互文档
UI 规则库
组件库使用规则
MVP 开发文档
MVP 验证报告
MVP 验证指标
企业级 PRD v2
企业级完整设计文档
企业级技术方案
完整开发文档
并行开发编排方案
分阶段开发提示词
部署上线计划
阶段验收清单
```

核心原则：

```text
先思考，再 PRD。
先 MVP，再完整系统。
先候选池，再企业级扩展。
先规则库，再 UI 实现。
先交互契约，再代码。
先确认依赖，再并行开发。
先人工确认，再进入下一步。
```

## 1. 总流程

完整流程如下：

```text
0. 可选边界 / 原始 idea（默认可跳过）
1. Ne/Ti/Ni/Te 产品思维流程
2. 第一轮 Te 输出：Ne/Ti/Ni/Te 过程文档 + MVP 初始化包 + 后续能力候选池
3. MVP PRD / MVP 范围定义
4. MVP UI 规则库 Lite
5. MVP UI 与交互设计
6. MVP 开发文档
7. MVP 实现与验证
8. MVP 验证报告
9. 企业级决策闸门
10. 第二轮 Ne/Ti/Ni/Te 企业级产品化
11. 企业级 PRD v2
12. 企业级 UI 规则库 Pro
13. 企业级完整 UI 设计
14. 企业级技术方案
15. 完整开发文档
16. 分阶段开发与验收
17. 测试、部署、上线与运维
18. 复盘、变更、迭代
```

这条流程有两条主路径：

```text
MVP 验证路径：
用于快速判断产品方向、主流程、核心价值是否成立。

企业级完整开发路径：
用于把已经验证的产品升级成可长期维护、可扩展、可交付的系统。
```

不能一开始就把完整企业级系统全部做完。

更稳的方式是：

```text
先用 MVP 验证价值，再用企业级流程补齐系统能力。
```

第一轮产品思考不是只产出 MVP，也不是提前实现完整系统。

第一轮的正确产物不是只有结论，而是带完整过程文档的输出。

至少包含三部分：

```text
Ne/Ti/Ni/Te 过程文档：
保留 Ne、Ti、Ni、Te 每个阶段的关键内容、判断、取舍和输出。

MVP 初始化包：
马上用于最小验证。

后续能力候选池：
保留第一轮发散中有价值、但不进入 MVP 的能力，供 MVP 通过后的第二轮企业级讨论使用。
```

这样可以同时做到：

```text
MVP 不膨胀。
未来能力不丢失。
前面讨论不丢失。
知道为什么这么做。
第二轮企业级开发有材料可接。
企业级 PRD、UI、技术方案可以回头查看推导依据。
```

从第一轮 Te 开始，`Ne/Ti/Ni/Te 过程文档` 就应该被视为正式上游文档。

它不是聊天记录的备份，也不是临时草稿，而是后续文档的依据索引：

```text
MVP PRD 查看它，确认最小范围为什么成立。
MVP UI 查看它，确认核心用户、场景和任务优先级。
MVP 开发文档查看它，确认哪些能力只做最小底座。
MVP 验证报告查看它，确认要验证哪些假设。
企业级 PRD v2 查看它，确认哪些候选能力应该重新讨论。
企业级 UI 设计查看它，确认不要推翻已验证主流程。
企业级技术方案查看它，确认哪些底层模型需要支持未来扩展。
完整开发文档查看它，确认阶段拆分和取舍依据。
```

因此，过程文档必须包含 `Ne / Ti / Ni / Te` 四个部分，后续企业级开发时可以作为查看文档反复引用。

## 2. 阶段闸门机制

本流程必须使用人工确认闸门。

AI 不允许自动跨阶段推进。

每个阶段都遵循：

```text
输入
-> AI 生成
-> 人工审查
-> 通过 / 修改 / 回退
-> 进入下一阶段
```

### 2.1 阶段状态

每个阶段都应显示状态：

```text
未开始
生成中
待人工确认
修改中
已通过
已回退
已暂停
```

### 2.2 阶段记录模板

```text
阶段名称：
阶段目标：
当前状态：
输入材料：
AI 输出：
人工确认结果：
需要修改的问题：
是否进入下一阶段：
```

### 2.3 不能自动推进的情况

遇到以下情况，AI 必须停止并询问：

```text
目标用户不清楚
核心场景不清楚
MVP 范围过大
页面任务不清楚
信息优先级不清楚
UI 规则库缺失
组件库不适合当前场景
技术方案存在明显分歧
验收标准无法判断
需求发生变化
```

## 3. 阶段 0：可选边界与原始 idea 输入（默认可跳过）

### 3.1 目标

只有在用户明确要求时，才把模糊想法整理成可以进入产品思考的输入。

默认情况下，不需要先整理输入。

如果用户已经开始自由表达，AI 直接进入 Ne-A 自由探索。

### 3.2 输入内容

可以是任意形式：

```text
一句想法
聊天记录
客户反馈
竞品观察
痛点描述
市场机会
已有业务流程
已有文档
```

### 3.3 AI 输出

仅当用户明确要求“先帮我整理边界”“先帮我定义问题”“先帮我明确目标”时，AI 才输出边界整理。

可选输出：

```text
本轮问题：
讨论范围：
期望产出：
限制条件：
已知信息：
缺失信息：
需要确认的问题：
```

### 3.4 提示词模板

这是可选提示词，不是进入 Ne-A 的前置条件。

```text
我会给你一个原始 idea。

请不要直接生成 PRD，也不要直接设计 UI。

请先帮我整理本轮讨论边界，输出：
1. 本轮真正要解决的问题
2. 讨论范围
3. 期望产出
4. 当前限制条件
5. 已知信息
6. 缺失信息
7. 需要我确认的问题

如果信息不足，请先问问题，不要自行脑补。

原始 idea：
[粘贴 idea]
```

### 3.5 人工确认点

如果跳过阶段 0，可以直接进入 Ne-A。

如果使用了阶段 0，再确认：

确认：

```text
这是不是我要解决的问题？
范围是否过大？
最终产出是否明确？
是否值得进入 Ne 发散？
```

## 4. 阶段 1：Ne/Ti/Ni/Te 产品思维流程

这一阶段用于把 idea 转化为可验证的产品方案。

推荐使用完整流程：

```text
Ne-A 自由探索
-> Ne-B 结构化整理
-> Ti 提纯
-> Ni 收束
-> Te 落地
```

不要只做 `Ne -> Te`。

如果发散后马上落地，容易把 PRD 写成功能清单，而不是产品方案。

### 4.1 Ne 发散

目标：

```text
打开可能性，找出用户、场景、痛点、机会、风险和功能形态。
```

Ne 阶段不要一开始就填模板。

真实发散往往会包含：

```text
为什么想做这个？
这个东西真的有必要做吗？
它可能只是一个念头吗？
做它的情绪、欲望、动机是什么？
有没有完全不同的产品形态？
有没有完全不是产品的可能？
如果不做会怎样？
如果做错了会怎样？
它更像产品、内容、工具、服务，还是一个表达？
```

因此 Ne 阶段分成两步：

```text
Ne-A 自由探索：
允许天马行空、跑题、质疑、联想、反方向思考，不急着输出结构化结论。
不讨论 MVP、最小版本、功能范围、开发计划或执行排期。

Ne-B 结构化整理：
把前面的自由素材整理成用户、场景、机会、风险、功能形态和验证假设。
```

### 4.1.1 Ne-A 自由探索

目标：

```text
把 idea 聊活，而不是立刻把它写死成产品需求。
```

这一阶段允许讨论不完全和开发相关的内容。

允许出现：

```text
个人动机
市场直觉
审美偏好
用户幻想
竞品联想
商业模式猜想
内容表达
技术灵感
反方向想法
暂时无关但可能启发项目的内容
```

AI 在这一阶段的角色不是填表产品经理，而是探索型合伙人。

AI 应该做：

```text
顺着动机继续聊
自然回应用户的联想
提出新的可能性
提出不同产品形态或非产品形态
捕捉反复出现的关键词
轻轻感知有价值但暂时跑题的内容
不要求用户补齐背景
不要求用户回答固定问题
```

AI 不应该做：

```text
不要先盘问用户
不要要求用户先输入完整背景
不要急着写 PRD
不要急着列功能清单
不要强行把所有话题拉回开发
不要把偶然联想都当成需求
不要因为用户跑题就打断探索
不要自动进入 Ti、Ni、Te
```

Ne-A 不设固定输出。

也就是说：

```text
不要求列表
不要求分类
不要求总结
不要求判断
不要求马上形成产品方向
不要求每次对话后都有结论
不要求完整背景
不要求目标清晰
不要求问题定义清楚
不讨论 MVP
不讨论最小可行版本
不讨论功能范围
不讨论开发计划
不讨论执行排期
```

AI 可以在内部轻轻记住线索，但不要主动把自由讨论变成表格。

Ne-A 的边界是：

```text
只发散，不筛选。
只打开，不收束。
只探索，不规划。
只允许可能性，不要求可执行。
```

如果讨论中自然冒出 MVP、最小版本、开发范围、执行步骤，AI 只需要轻轻放下：

```text
这个先记着，等后面 Te 或 MVP 阶段再处理。现在先继续自由发散。
```

只有当用户明确说：

```text
整理一下
收一下
进入下一步
开始结构化
进入 Ne-B
```

才开始进入结构化整理。

Ne-A 的启动方式可以很简单：

```text
我们先自由聊，不急着整理成产品文档。
```

### 4.1.2 Ne 阶段跑题处理机制

Ne 阶段允许跑题，但跑题要被管理。

这里的管理不是要求用户按格式说话，也不是要求 AI 立刻输出分类。

它只是 AI 在后台保持一点方向感。

AI 可以在心里把内容粗略感知为四类：

```text
核心相关：
直接影响当前 idea 的用户、场景、价值、功能、风险。

间接相关：
暂时不影响当前 MVP，但可能进入后续能力候选池。

灵感素材：
可能未来有用，但现在不进入产品讨论。

真正偏离：
和当前项目关系很弱，可以记录后暂时放下。
```

Ne-A 阶段不要求输出跑题记录表。

如果用户要求“帮我整理刚才跑远的东西”，才可以进入 Ne-B 或单独输出整理结果。

AI 可以在适当时候温和收束：

```text
这个方向有意思，我先把它记为灵感素材。我们现在要不要继续沿着它聊，还是回到当前 idea 的核心问题？
```

### 4.1.3 Ne-A 的出口选择

Ne-A 结束时不一定进入产品开发。

可能出口包括：

```text
继续 Ne-A：
还没有聊透，继续自由探索。

进入 Ne-B：
素材已经足够，可以结构化整理。

回到阶段 0：
发现原始问题定义错了，需要重新定义边界。

先做调研：
缺少用户、市场、技术或竞品信息，暂不进入 PRD。

缩小 idea：
原 idea 太大，先选择一个更小切口。

暂停或放弃：
暂时没有足够理由继续做。
```

Ne-A 的出口判断由用户触发，不固定使用模板。

当用户说“整理一下”“下一步呢”“这个还有必要做吗”时，AI 可以用自然语言给出建议。

建议只需要回答：

```text
继续自由聊，还是开始整理？
现在是进入产品化，还是先调研、缩小、暂停或放弃？
为什么？
```

不要默认必须进入产品开发。

### 4.1.4 Ne-B 结构化整理

目标：

```text
把自由探索中的材料整理成可以进入 Ti 提纯的素材池。
```

AI 输出：

```text
可能用户：
使用场景：
用户痛点：
潜在机会：
潜在风险：
竞品或类比对象：
可能功能：
值得验证的假设：
明显不值得继续的方向：
需要进入 Ti 提纯的问题：
```

提示词：

```text
请进入 Ne-B 结构化整理阶段。

请把刚才 Ne-A 自由探索的内容整理成结构化发散结果：
1. 可能用户
2. 使用场景
3. 用户痛点
4. 潜在机会
5. 潜在风险
6. 竞品或类比对象
7. 可能产品形态
8. 值得验证的假设
9. 明显不值得继续的方向
10. 需要进入 Ti 提纯的问题

要求：
- 不要新增太多没聊过的内容
- 保留自由探索中的关键直觉
- 区分核心相关、间接相关、灵感素材和真正偏离
- 不要直接写 PRD
- 不要自动进入 Ti，等待人工确认
```

人工确认点：

```text
自由探索是否聊够？
结构化整理是否保留了关键直觉？
哪些方向要进入 Ti？
哪些方向放入后续能力候选池？
哪些灵感素材暂时搁置？
是否需要继续 Ne-A？
```

### 4.2 Ti 提纯

目标：

```text
从发散材料中提炼真实需求、业务逻辑、数据对象、约束条件和关键假设。
```

AI 输出：

```text
真实需求：
伪需求或低优先级需求：
核心业务对象：
对象之间的关系：
核心动作：
权限与角色：
关键约束：
关键假设：
逻辑矛盾：
```

提示词：

```text
请进入 Ti 提纯阶段。

基于 Ne 阶段结果，请你：
1. 区分真实需求和伪需求
2. 提炼核心业务对象
3. 梳理对象之间的关系
4. 梳理用户动作和系统动作
5. 找出权限、数据、流程、商业上的约束
6. 找出必须验证的关键假设
7. 指出当前逻辑矛盾

不要新增功能幻想，重点做逻辑整理。
```

人工确认点：

```text
这些需求真实吗？
核心对象是否正确？
关键约束是否遗漏？
是否存在无法自洽的逻辑？
```

### 4.3 Ni 收束

目标：

```text
凝结产品主轴，确定核心用户、核心场景、核心闭环和 MVP 方向。
```

AI 输出：

```text
产品定位：
核心用户：
核心场景：
核心问题：
核心闭环：
MVP 假设：
第一版不做什么：
成功判断：
```

提示词：

```text
请进入 Ni 收束阶段。

基于前面的发散和提纯结果，请收束为一个清晰的产品方向：
1. 产品定位
2. 核心用户
3. 核心场景
4. 核心问题
5. 核心闭环
6. MVP 假设
7. 第一版不做什么
8. 成功判断

要求：
- 宁愿小而清晰，不要大而模糊
- 必须形成一个可验证的主流程
- 明确舍弃项
```

人工确认点：

```text
产品主轴是否成立？
MVP 假设是否可验证？
第一版范围是否足够小？
是否可以进入 PRD？
```

### 4.4 Te 落地

目标：

```text
把产品方向转化为三个结果：
1. Ne/Ti/Ni/Te 过程文档
2. MVP 初始化包
3. 后续能力候选池
```

AI 输出：

```text
Ne/Ti/Ni/Te 过程文档：
产品方向确认：
MVP 初始化包：
后续能力候选池：
暂不考虑清单：
关键假设：
MVP 验证指标：
MVP 通过后再讨论的问题：
```

Te 不能只输出最终 MVP。

它必须保留前面 Ne、Ti、Ni 的关键内容，否则最后文档会丢失讨论过程，只剩执行结论。

更准确地说，Te 阶段应该把前面的所有阶段沉淀成一份可查看的过程文档。

这份过程文档不是最终需求文档，但它是后续所有正式文档的依据。

Te 的输出需要回答：

```text
我们为什么选择这个方向？
哪些想法被保留？
哪些想法被放入候选池？
哪些想法被舍弃？
哪些判断来自 Ti 的逻辑提纯？
哪些判断来自 Ni 的主轴收束？
这个 MVP 是如何从前面的讨论推导出来的？
```

### 4.4.0 Ne/Ti/Ni/Te 过程文档

过程文档用于保留完整思考链。

它不是完整聊天记录，也不是逐字稿。

它是把每个阶段的重要内容、阶段结论、取舍依据保存下来。

这份文档在 MVP 之后仍然重要。

企业级开发阶段可以用它来查看：

```text
为什么当初选择这个方向？
为什么 MVP 只做这些？
哪些功能当初被后置？
哪些想法被判断为伪需求？
哪些假设还没有验证？
企业级扩展应该从哪些候选能力开始？
哪些方向当初明确不做？
```

过程文档建议结构：

```text
文档信息：
- 项目 / 想法名称
- 生成时间
- 当前阶段
- 适用范围

0. 原始 idea 与上下文：
- 原始想法
- 讨论背景
- 用户自然表达中的关键线索

1. Ne-A 自由探索记录：
- 反复出现的直觉
- 有价值的动机
- 重要联想
- 非产品形态的可能
- 暂时跑题但有启发的素材
- 暂时不判断、不筛选的开放问题

2. Ne-B 结构化整理：
- 可能用户
- 可能场景
- 可能产品形态
- 潜在机会
- 潜在风险
- 竞品或类比
- 值得验证的假设
- 明显不值得继续的方向

3. Ti 提纯记录：
- 被判断为真实的问题
- 被判断为伪需求或低优先级的内容
- 核心业务对象
- 对象关系
- 关键约束
- 重要逻辑矛盾
- 必须验证的关键假设
- 仍不确定的问题

4. Ni 收束记录：
- 一句话主轴
- 核心用户
- 核心场景
- 核心闭环
- 被保留的方向
- 被舍弃的方向
- 被后置的方向
- 进入 MVP 的理由

5. Te 落地记录：
- 产品方向确认
- MVP 初始化包
- 后续能力候选池
- 暂不考虑清单
- 关键假设
- MVP 验证指标
- MVP 通过后再讨论的问题
```

过程文档的原则：

```text
不复制全部对话。
不写成会议纪要。
不丢失关键判断。
不只保留最终结论。
Ne / Ti / Ni / Te 四个阶段都要有。
每个重要取舍都要能追溯原因。
后续企业级开发可以回头查看。
```

### 4.4.0.1 过程文档在企业级开发中的使用方式

企业级开发不是从零重新发散，也不是把候选池里的所有功能一次性做完。

它应该先读取第一轮过程文档，再结合 MVP 验证报告进入第二轮产品化。

过程文档在企业级阶段的作用是：

```text
作为来源：
说明正式版需求从哪里来，不让企业级 PRD 变成凭空扩写。

作为边界：
说明哪些能力已验证、哪些只是候选、哪些曾经明确不做。

作为取舍依据：
说明为什么某些功能进入正式版第一期，为什么某些功能继续后置。

作为设计依据：
说明核心用户、核心场景、核心任务和信息优先级，防止 UI 只追求好看。

作为技术依据：
说明核心业务对象、状态、权限、记录、候选扩展，帮助架构预留合理空间。

作为变更依据：
当企业级开发过程中出现新需求时，用它判断是延续主轴、修正主轴，还是跑偏。
```

企业级阶段读取过程文档时，应重点查看：

```text
Ne-A：
原始动机、反复出现的直觉、非产品化可能、暂时跑题但有启发的素材。

Ne-B：
用户、场景、机会、风险、候选功能、被搁置的方向。

Ti：
真实需求、伪需求、核心对象、约束、逻辑矛盾、关键假设。

Ni：
产品主轴、核心闭环、保留/舍弃/后置的方向、进入 MVP 的理由。

Te：
MVP 初始化包、后续能力候选池、验证指标、MVP 后再讨论的问题。
```

这样企业级开发不是简单地“做大”，而是从已验证的主轴上“做完整、做稳定、做可交付”。

第一轮 Te 不是把所有功能都塞进 PRD。

它要完成一次需求分流：

```text
A. MVP 必须做
不做就无法验证核心假设。

B. MVP 最小底座
现在只做最小形态，但要避免未来推倒重来。

C. MVP 后候选
有价值，但等 MVP 验证通过后再展开。

D. 暂不考虑
当前没有证据支持，或复杂度过高，先放弃。
```

### 4.4.1 MVP 初始化包

MVP 初始化包用于马上进入最小验证。

它包含：

```text
MVP 核心假设：
MVP 目标用户：
MVP 使用场景：
MVP 主流程：
MVP 页面清单：
MVP 必做功能：
MVP 最小底座：
MVP 不做清单：
MVP UI 规则 Lite：
MVP 开发输入：
MVP 验证指标：
```

MVP 必做功能的判断标准：

```text
如果去掉这个功能，核心假设无法验证，它就是 MVP 必做。
如果去掉这个功能，体验变差但仍能验证，它不是 MVP 必做。
如果这个功能主要服务规模化、管理化、自动化，它通常属于 MVP 后候选。
```

MVP 最小底座是一个容易被忽略的部分。

它不是完整企业级能力，但要为后续留下结构空间。

示例：

```text
任务审核系统 MVP 必做：
- 任务列表
- 任务详情
- 通过
- 驳回
- 基础状态反馈

MVP 最小底座：
- 基础用户身份
- 任务状态字段
- 操作人字段
- 操作时间字段
- 基础权限判断
- 基础操作记录

MVP 后候选：
- 多级审核流
- 角色权限配置
- 审计日志
- 批量审核
- 消息通知
- 数据报表
- 导入导出
- 组织架构
```

原则：

```text
MVP 不做企业级完整功能。
MVP 也不能把未来完全堵死。
```

### 4.4.2 后续能力候选池

后续能力候选池用于保存第一轮发散中暂不进入 MVP、但未来可能重要的内容。

它不是开发承诺。

它只是第二轮企业级讨论的素材池。

候选池可以分为：

```text
企业级功能候选：
高级权限候选：
数据分析候选：
自动化能力候选：
配置化能力候选：
协作能力候选：
消息通知候选：
导入导出候选：
审计与日志候选：
部署上线要求候选：
安全与合规候选：
性能与稳定性候选：
商业化能力候选：
```

每个候选能力建议记录：

```text
能力名称：
来源：
解决的问题：
相关用户：
可能价值：
复杂度：
为什么不进 MVP：
MVP 后触发条件：
```

示例：

```text
能力名称：批量审核
来源：Ne 发散阶段的运营高频处理场景
解决的问题：单条审核效率低
相关用户：运营人员、审核主管
可能价值：提高处理效率
复杂度：中
为什么不进 MVP：单条审核足以验证核心流程
MVP 后触发条件：真实任务量较大，单条审核成为明显瓶颈
```

### 4.4.3 暂不考虑清单

暂不考虑清单用于主动删除诱人但当前不该做的内容。

它和候选池不同。

```text
候选池：
可能以后做，需要保留。

暂不考虑：
当前没有证据支持，短中期不进入讨论。
```

暂不考虑的常见原因：

```text
偏离核心用户
偏离核心场景
无法验证核心假设
复杂度远大于收益
需要大量外部资源
当前没有真实需求证据
会拖慢 MVP 验证
```

提示词：

```text
请进入 Te 落地阶段。

基于已经确认的产品方向，请做第一轮 Te 输出。

必须包含：
1. Ne/Ti/Ni/Te 过程文档
2. 产品方向确认
3. MVP 初始化包
4. 后续能力候选池
5. 暂不考虑清单
6. 关键假设
7. MVP 验证指标
8. MVP 通过后再讨论的问题

Ne/Ti/Ni/Te 过程文档必须保留：
- Ne-A 中有价值的直觉、动机、联想
- Ne-B 中整理出的用户、场景、机会、风险
- Ti 中提纯出的真实问题、伪需求、约束、矛盾
- Ni 中收束出的主轴、核心闭环、舍弃理由
- Te 中形成的 MVP 初始化包、候选池、暂不考虑清单和验证指标

请把所有需求分为四类：
A. MVP 必须做
B. MVP 最小底座
C. MVP 后候选
D. 暂不考虑

要求：
- MVP 必须足够小，可以快速验证核心假设
- MVP 最小底座只保留未来不应推倒重来的结构
- MVP 后候选只记录，不实现
- 暂不考虑清单要说明为什么暂不考虑

注意：
- 这是草案，不是最终开发文档
- 不要展开企业级完整系统
- 优先服务 MVP 验证
- 但不要丢失未来可能进入企业级阶段的高价值候选能力
- 也不要丢失前面 Ne / Ti / Ni 阶段形成的重要判断和取舍理由
- 过程文档必须作为后续企业级产品化、UI 设计、技术方案的查看依据
```

## 5. 阶段 2：MVP PRD 产品需求文档

### 5.1 PRD 的作用

PRD 负责回答：

```text
为什么做？
给谁用？
解决什么问题？
用户怎么完成业务？
系统需要支持什么规则？
什么算完成？
```

PRD 不直接驱动代码。

PRD 应先转化为 UI、交互和开发输入。

### 5.2 PRD 标准结构

```text
1. 产品背景
2. 目标用户
3. 用户场景
4. 用户问题

9. 功能需求
10. 数据对象
11. 权限规则
12. 状态规则
13. 异常规则
14. 不做清单
15. MVP 范围
16. 验收标准
17. 待确认问题
```

### 5.3 PRD 生成提示词

```text
请基于已经确认的产品方向生成 PRD。

要求：
1. 先写产品背景和目标用户

3. 写清核心流程

8. 写清状态和异常
9. 写出不做清单
10. 写出 MVP 验收标准
11. 引用 Ne/Ti/Ni/Te 过程文档，说明 MVP 范围如何从前序讨论推导出来

请不要直接生成 UI 页面，也不要写代码。
```

### 5.4 人工确认点

```text

核心流程是否正确？

不做清单是否明确？
是否可以进入 MVP 范围定义？
```

## 6. 阶段 3：MVP 范围定义

### 6.1 MVP 的目标

MVP 不追求完整。

MVP 只验证：

```text
这个方向是否成立？
核心用户是否存在？
主流程是否可跑通？
核心功能是否有价值？
用户是否愿意继续使用？
```

### 6.2 MVP 产物

```text
MVP 用户
MVP 场景
MVP 核心流程
MVP 页面清单
MVP 功能清单
MVP 不做清单
MVP UI 范围
MVP 技术范围
MVP 验证指标
```

### 6.3 MVP 范围提示词

```text
请基于 PRD 定义 MVP 范围。

要求：
1. 明确 MVP 只验证哪个核心假设
2. 明确 MVP 的目标用户
3. 明确 MVP 的核心流程
4. 列出必须做的页面
5. 列出必须做的功能
6. 列出暂时不做的功能
7. 列出可以模拟、手动或假数据处理的部分
8. 给出 MVP 验证指标

要求范围尽可能小，但必须能完成主任务。
```

### 6.4 MVP 判断标准

MVP 范围通过的标准：

```text
主用户清楚
主任务清楚
核心流程闭环
页面数量可控
功能没有过度扩张
不做清单明确
验证指标可观察
```

## 7. 阶段 4：UI 规则库机制

### 7.1 UI 规则库是什么

UI 规则库是 AI UI 开发的护栏。

它不是美化素材包，而是一组设计、交互和工程约束：

```text
用户体验规则
信息分层规则
交互模式规则
布局规则
组件使用规则
样式 token 规则
CSS 实现规则
状态反馈规则
可访问性规则
反模式清单
评审清单
```

它解决的问题是：

```text
AI 会不会乱堆功能？
AI 会不会乱用组件？
AI 会不会随便写颜色和间距？
AI 会不会没有用户路径？
AI 会不会写出能跑但不好用的页面？
```

### 7.2 MVP 阶段是否需要 UI 规则库

需要。

但 MVP 阶段使用轻量规则库：

```text
MVP UI Rules Lite
```

MVP 不需要完整设计系统，但必须保证：

```text
主任务清晰
信息优先级清楚
基础布局稳定
交互容器正确
状态反馈完整
按钮优先级正确
危险操作有确认
颜色和间距不乱
不要堆功能
不要随意换风格
```

企业级阶段再升级为：

```text
Enterprise UI Rules Pro
```

### 7.3 UI 规则库推荐结构

```text
/ui-rules
  00-principles.md
  01-product-types.md
  02-layout-patterns.md
  03-interaction-patterns.md
  04-component-rules.md
  05-style-tokens.md
  06-css-layout-rules.md
  07-state-rules.md
  08-accessibility-rules.md
  09-anti-patterns.md
  10-examples.md
  11-review-checklist.md
  /libraries
    vant.md
    antd.md
    element-plus.md
    tdesign.md
    semi.md
    arco.md
    shadcn.md
```

### 7.4 UI 规则条目格式

每条规则建议使用结构化格式：

```text
规则 ID：
规则名称：
适用场景：
优先级：
规则内容：
禁止事项：
正例：
反例：
验收标准：
关联组件：
关联 token：
```

示例：

```text
规则 ID：table.action-density
规则名称：表格行操作密度控制
适用场景：表格行内操作超过 2 个时
优先级：高
规则内容：
- 行内最多展示 2 个高频操作
- 其他操作进入“更多”菜单
- 危险操作放在菜单底部
- 危险操作必须二次确认
禁止事项：
- 不要把 3 个以上按钮平铺在同一行
- 不要把主操作藏进更多菜单
验收标准：
- 每行可见操作不超过 2 个
- 删除、驳回等危险操作有确认弹窗
```

### 7.5 开发前如何使用 UI 规则库

AI 在设计或实现页面前，必须先输出规则引用报告：

```text
本页面类型：
适用布局规则：
适用交互规则：
适用组件规则：
适用状态规则：
适用样式 token：
适用组件库规则：
规则库缺口：
需要新增或调整的规则：
```

提示词：

```text
请先读取 UI 规则库，不要直接写代码。

基于当前 PRD 和页面任务，请输出：
1. 本页面类型
2. 适用的 UI 规则
3. 适用的布局模式
4. 适用的组件模式
5. 适用的交互模式
6. 适用的状态规则
7. 适用的 token
8. 哪些信息应该默认显示
9. 哪些信息应该延迟展示
10. 是否存在规则库未覆盖的问题

如果规则库不足，请先提出规则补充建议，等待确认后再继续。
```

### 7.6 开发后如何审查 UI 规则

提示词：

```text
请根据 UI 规则库审查当前页面实现。

重点检查：
1. 是否符合用户主任务
2. 是否符合信息优先级
3. 是否错误使用组件
4. 是否存在按钮过多
5. 是否缺少状态反馈
6. 是否 token 使用不一致
7. 是否布局拥挤或视觉混乱
8. 是否有权限、错误、空状态
9. 是否违反反模式清单
10. 给出最小修改建议

不要重写整个页面，优先给出最小修正。
```

### 7.7 如何新增规则

新增规则流程：

```text
发现问题
-> 判断是否重复出现
-> 提炼成通用规则
-> 归入对应分类
-> 增加正例和反例
-> 增加验收标准
-> 下次开发引用
```

不要因为一次偶然偏好就新增规则。

只有当它能防止重复跑偏，才值得进入规则库。

### 7.8 如何从已有资料提炼 UI 规则

UI 规则库可以来自：

```text
已有 UI 文档
交互设计知识库
CSS 设计知识库
GitHub 项目文档
组件库官方文档
优秀产品截图
项目开发中的问题记录
人工设计评审意见
```

但不要把这些资料直接丢给 AI 复制。

正确流程是：

```text
收集资料
-> 判断适用场景
-> 提炼设计模式
-> 转成项目规则
-> 增加验收标准
-> 加入规则库
```

示例：

```text
原始资料：
GitHub 上有一个列表页示例，包含筛选、表格、行操作、详情面板。

不要这样使用：
照着这个页面做一个类似的。

应该提炼为规则：
- 当页面主任务是浏览和处理对象时，主体使用列表或表格。
- 高频筛选放在列表上方。
- 高级筛选默认折叠。
- 行内操作不超过 2 个。
- 详情使用抽屉或详情页承载。
- 危险操作必须二次确认。
- 批量操作只在选中数据后显示。
```

CSS 资料也应该转成规则，而不是变成零散样式：

```text
不要只复制 CSS。

应该提炼：
- 页面内容区 padding
- 表格行高
- 按钮间距
- 表单 label 宽度
- 抽屉宽度
- 响应式断点
- token 命名方式
```

如果直接使用外部代码，需要检查 license。

如果只是学习设计模式并转化为项目规则，风险更低，也更适合长期复用。

### 7.9 UI 规则库与美观的关系

UI 规则库不能保证每个页面都有顶级审美。

但它可以稳定提升基础质量：

```text
页面不乱
信息有层级
操作有主次
组件使用统一
颜色和间距稳定
状态反馈完整
交互模式一致
代码更容易维护
```

这些是企业级 UI 的基础美感。

如果项目需要更强的品牌感、视觉张力、动效、插画或营销表达，需要额外补充：

```text
品牌视觉规范
视觉参考样例
高保真设计稿
人工审美评审
动效规范
图片和插画资产
```

因此可以这样理解：

```text
UI 规则库负责让 AI 不乱。
组件库负责让实现稳定。
品牌视觉负责让产品有个性。
人工评审负责判断是否真正好看。
```

## 8. 阶段 4.1：组件库规则

### 8.1 组件库可以作为规则吗

可以。

Vant、Ant Design、Element Plus、TDesign、Semi、Arco、Material UI、shadcn/ui 等组件库，都可以成为 UI 规则库的一部分。

但组件库不等于完整 UI 规则库。

组件库解决：

```text
组件实现
组件状态
默认样式
主题能力
基础交互
```

项目 UI 规则库还要解决：

```text
用户任务
信息优先级
页面结构
业务权限
MVP 取舍
产品体验判断
```

正确关系是：

```text
项目 UI 规则库 = 产品规则 + 交互规则 + 布局规则 + 组件库规则 + 样式 token + 工程约束
```

### 8.2 组件库选择原则

```text
移动端 H5 / 小程序风格：Vant、TDesign Mobile
企业后台：Ant Design、Element Plus、TDesign、Semi、Arco
AI 工具 / 现代 SaaS：shadcn/ui、Radix、Tailwind、Material UI
数据可视化：ECharts、AntV
流程图 / 节点编辑：React Flow
代码编辑：Monaco Editor
```

一个项目应尽量保持：

```text
1 个主 UI 组件库
1 套设计 token
1 套布局规则
1 套交互规则
```

不要混用多个同类 UI 库。

可以有专业辅助库，但要明确边界：

```text
主 UI：Ant Design
图表：ECharts
流程图：React Flow
编辑器：Monaco Editor
```

### 8.3 组件库规则模板

```text

## 1. 适用场景
这个组件库适合什么产品、端、页面。

## 2. 不适用场景
哪些情况不要用它。

## 3. 默认组件映射
按钮：
表单：
表格：
弹窗：
抽屉：
通知：
列表：
导航：
分页：
上传：

## 4. 交互规则
确认、提交、删除、筛选、分页、加载、空状态怎么做。

## 5. 样式规则
颜色、字号、间距、圆角、密度、暗色模式怎么处理。

## 6. 二次封装规则
哪些组件必须封装成项目组件。

## 7. 禁止项
不要混用别的库的同类组件。

```

### 8.4 Vant 示例规则

```text
组件库：Vant

适用场景：
- 移动端 H5
- 小程序风格页面
- 轻量业务应用
- 表单、列表、详情、提交类流程

不适用场景：
- 高密度企业后台
- 复杂数据表格
- 大屏数据分析
- 多窗口管理系统

组件规则：
- 主按钮使用 Button type="primary"
- 危险操作使用 Button type="danger"
- 表单使用 Form + Field
- 列表使用 Cell / List
- 详情和操作可使用 Popup / ActionSheet
- 反馈使用 Toast / Dialog

交互规则：
- 移动端不要使用复杂表格
- 底部主操作固定在安全区域上方
- 危险操作必须使用 Dialog 确认
- 长列表必须考虑加载中、空状态、错误重试
```

### 8.5 组件库开发提示词

```text

- 不要自造组件库已有能力
- 不要混用其他 UI 库的同类组件
- 样式优先使用主题 token

- 如果组件库无法满足需求，先提出补充方案，不要直接乱写
```

## 11. 阶段 7：MVP 实现与验证

### 11.1 MVP 验证目标

MVP 验证不是只看功能有没有写完。

它要验证：

```text
用户是否能完成主任务
核心流程是否顺畅
页面信息是否清楚
核心功能是否有价值
错误和异常是否可恢复
UI 是否没有明显跑偏
```

### 11.2 MVP 指标

可以从四类指标判断。

任务指标：

```text
主任务完成率
完成主任务所需步骤
用户卡住的位置
关键操作点击成功率
```

体验指标：

```text
用户是否知道下一步做什么
用户是否能找到主要操作
是否存在信息过载
是否存在误操作
```

功能指标：

```text
核心功能是否可用
核心状态是否完整
异常是否可恢复
权限是否正确
```

产品指标：

```text
用户是否愿意继续使用
是否验证了核心假设
是否值得进入下一阶段
是否需要改变方向
```

### 11.3 MVP 验证提示词

```text
请基于 MVP 开发结果进行验证评审。

请检查：
1. 用户主任务是否可以完成
2. 核心流程是否闭环
3. 页面信息是否清楚
4. 操作入口是否明确
5. loading、empty、error、success、permissionDenied 是否完整
6. 是否符合 UI 规则库
7. 是否符合组件库规则
8. 是否存在功能过度开发
9. 是否存在 UI 跑偏
10. 是否达到了 MVP 验证指标

请输出：
- 通过项
- 问题项
- 最小修改建议
- 是否建议进入企业级决策闸门和第二轮产品化
```

### 11.4 MVP 后的决策

MVP 完成后不能默认进入完整开发。

必须选择：

```text
继续：核心假设成立，进入企业级决策闸门和第二轮产品化。
修改：方向基本成立，但主流程或 UI 需要调整。
回退：MVP 范围或 PRD 有问题，需要回到前面阶段。
终止：核心假设不成立，停止该方向。
```

### 14.4 企业级非功能需求

企业级开发必须把非功能需求写进文档。

常见非功能需求：

```text
性能：
页面加载时间、接口响应时间、列表数据量、并发量。

并发与容量：
同时在线用户、QPS、任务队列、批处理规模、峰值提醒量、冲突处理。

安全：
登录、鉴权、权限隔离、敏感数据保护、敏感操作确认。

稳定性：
错误恢复、重试机制、降级策略、异常告警。

可靠性与恢复：
数据持久化、崩溃恢复、备份恢复、幂等处理、离线可用、灾难恢复。

隐私：
数据分类、最小采集、用户授权、第三方模型数据发送说明、数据删除。

可观测性：
日志、指标、追踪、崩溃记录、健康检查、告警、关键业务事件。

可维护性：
模块边界、组件复用、代码规范、文档规范。

可扩展性：
角色扩展、流程扩展、字段扩展、配置扩展。

兼容性与可移植性：
系统版本、设备规格、浏览器或运行环境、时区、语言、弱网、离线。

可访问性与可用性：
对比度、字号、动效可关闭、键盘/读屏、错误可恢复、任务可完成。

部署：
测试环境、预发环境、生产环境、配置管理、回滚策略。

成本与资源：
云服务费用、AI token 消耗、本地模型资源、存储增长、电量和流量。
```

非功能需求不能只写“需要高性能”“需要安全”。

必须尽量写成可判断的设计项：

```text
指标：
例如启动时间、页面响应、接口超时、最大列表数据量、通知调度数量。

策略：
例如分页、缓存、队列、限流、重试、降级、幂等、索引、批处理。

验收：
例如在指定数据量、设备、网络条件下完成主任务，不丢数据，不假成功。
```

## 21. 变更与返工机制

流程不是写死的。

如果过程中发现问题，可以回退。

但回退必须有依据。

### 21.1 常见回退路径

```text
UI 设计不清楚 -> 回到 MVP UI 与交互设计
MVP 范围过大 -> 回到 MVP 范围定义
核心流程不成立 -> 回到 PRD
产品方向不成立 -> 回到 Ni 收束
需求逻辑混乱 -> 回到 Ti 提纯
想法方向不足 -> 回到 Ne 发散
UI 实现跑偏 -> 回到 UI 规则库和交互蓝图
组件库不适合 -> 回到组件库选择规则
```

### 21.2 变更记录模板

```text
变更编号：
提出时间：
提出原因：
影响阶段：
影响页面：
影响功能：
影响 UI 规则：
修改方案：
是否需要回退：
人工确认结果：
```

### 21.3 防跑偏规则

```text
AI 不允许跳过人工确认。
AI 不允许在 MVP 阶段扩展完整系统。
AI 不允许脱离 UI 规则库设计页面。
AI 不允许混用未确认的组件库。
AI 不允许用“更好看”为理由改变主流程。
AI 不允许在信息不足时自行脑补关键业务规则。
```

## 23. 一次完整协作的总控提示词

```text
我会和你一起从一个原始 idea 推进到可开发项目。

请遵守以下流程：
1. 默认直接进入 Ne-A 自由探索，不要先盘问我，也不要先明确问题边界
2. Ne-A 只做自由聊天，不急着产品化
3. 只有我确认“整理/解析/结构化”后，再进入 Ne-B 结构化整理
4. 再进入 Ti 提纯、Ni 收束、Te 落地
5. 第一轮 Te 输出 Ne/Ti/Ni/Te 过程文档、MVP 初始化包和后续能力候选池
6. 生成 MVP PRD 和 MVP 范围
7. 匹配或生成 MVP UI 规则库 Lite
8. 生成 MVP UI 与交互蓝图
9. 生成 MVP 开发文档
10. 生成 MVP 验证指标
11. MVP 完成后生成 MVP 验证报告
12. MVP 通过后，基于 Ne/Ti/Ni/Te 过程文档、验证报告和候选池进入第二轮企业级产品化
13. 生成企业级 PRD v2
14. 生成企业级 UI 规则库 Pro 和企业级 UI 设计
15. 生成企业级技术方案
16. 生成完整开发文档、阶段依赖关系、并行开发编排方案和分阶段开发提示词
17. 生成测试、部署、上线和运维计划

重要规则：
- 每个阶段完成后必须等待我确认
- 不允许自动进入下一阶段
- Ne-A 阶段信息不足也不要先盘问，先自然对话
- Ne-A 阶段允许自由探索、质疑、跑题、暂停或放弃
- Ne-A 阶段不要强行生成 PRD 或开发计划
- Ne-A 阶段不要输出固定模板、表格或清单
- Ne-A 阶段只做纯发散，不讨论 MVP、最小版本、功能范围、开发计划
- AI 可以在后台感知跑题方向，但不要把跑题内容全部当成需求
- Te 阶段必须生成 Ne/Ti/Ni/Te 过程文档，四个阶段都要有，不只输出 MVP 结论
- 企业级产品化、UI 设计、技术方案、完整开发文档都可以引用这份过程文档查看依据
- MVP 通过后进入企业级开发前，必须先回看过程文档和 MVP 验证报告
- 企业级阶段新增的功能必须说明来源：已验证、候选池、用户反馈、新增需求或技术必要
- 不要在 MVP 阶段扩展完整系统
- 第一轮后续能力候选池只记录，不实现
- MVP 通过后不能直接完整开发，必须先做第二轮企业级产品化
- UI 设计必须引用 UI 规则库
- 组件实现必须引用组件库规则
- 企业级 PRD、企业级技术方案和完整开发文档必须包含非功能性设计，覆盖性能、并发与容量、可靠性、恢复能力、安全、隐私、可观测性、兼容性、可维护性、成本与资源
- 完整开发文档必须包含阶段依赖关系、非功能性设计清单、并行开发编排方案、每阶段开发提示词和验收标准
- 并行开发编排必须至少包含：第 0 步确认数据模型和依赖，第 1 步基础阶段单独完成，第 2 步页面骨架与视觉 token 并行，第 3 步详情、提醒、AI 等业务模块并行，第 4 步备份恢复，第 5 步集成联调，第 6 步发布前整理
- 部署上线必须包含测试、环境、监控和回滚
- 如果发现跑偏，必须指出应回退到哪个阶段

现在请直接进入 Ne-A 自由聊天。

原始 idea：
[粘贴 idea]
```

## 24. 最短工作口诀

```text
先发散，后收束。
先 PRD，后 UI。
先 MVP，后完整。
先候选，后扩展。
先规则，后实现。
先依赖，后并行。
先验收，后推进。
先部署，后上线。
先回退，后硬改。
```

最终目标不是让 AI 一次生成完美项目。

最终目标是让 AI 在一个有边界、有规则、有确认、有返工机制的流程里，持续生成可判断、可修改、可开发、可验收的结果。
